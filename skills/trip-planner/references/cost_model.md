# 费用口径

**一条红线：实时报价与经验估算永不混列。**

同程查到的是真金白银的当前报价；餐饮、市内交通只能按经验推算。
把两者混进同一列求和，用户会以为整份预算同样可靠。所以 `cost_table.py`
强制分成 🟢 / 🟡 两张表，各自小计，最后才合并。

---

## 分类标准

| 项目 | 归类 | 数据来源 |
| --- | --- | --- |
| 往返机票 | 🟢 实时报价 | `tc_query.sh flight` |
| 往返火车 | 🟢 实时报价 | `tc_query.sh train` |
| 长途汽车 | 🟢 实时报价 | `tc_query.sh bus` |
| 住宿 | 🟢 实时报价 | `tc_query.sh hotel` |
| 景区门票 | 🟢 实时报价 | `tc_query.sh scenery` |
| 度假产品/跟团 | 🟢 实时报价 | `tc_query.sh travel` |
| 市内交通（地铁/公交/打车） | 🟡 估算 | 经验值 |
| 餐饮 | 🟡 估算 | 经验值 |
| 购物/纪念品 | 🟡 估算 | 经验值，默认不计入 |
| 搜索结果里提到的票价 | 🟡 估算 | anysearch 抓来的价格可能过时 |

**判定口径**：能点进去下单的才算 🟢。搜索文章里写的「门票 60 元」不算，
因为它可能是三年前的价格 —— 归 🟡，并在 `basis` 里写明来源与年份。

## 估算基准（可按城市调整）

这些是缺省值，写进 `basis` 字段时要说明依据，不要装成精确数字。

| 项目 | 一线城市 | 二线城市 | 说明 |
| --- | ---: | ---: | --- |
| 市内交通 | ¥50/人/天 | ¥35/人/天 | 地铁为主 + 少量打车 |
| 餐饮（经济） | ¥100/人/天 | ¥80/人/天 | 快餐 + 小馆子 |
| 餐饮（中等） | ¥180/人/天 | ¥140/人/天 | 正经餐厅一日三餐 |
| 餐饮（品质） | ¥350/人/天 | ¥260/人/天 | 含一顿人均 150+ 的正餐 |

用户明确说了预算档次就用对应档；没说默认「中等」，并在报告里写明假设。

## 数据流

```
tc_query.sh <type> --prices
        ↓  {items:[{name, price, section, ...}]}
   agent 挑选具体班次/酒店/门票
        ↓  写成 cost.json 的 quoted[] 条目，source 注明 "同程 xxx-query"
cost_table.py cost.json
        ↓
   ├─ --format markdown      → 报告里的费用明细节
   └─ --format routes-cost   → {day: 金额}，填进 routes[].cost
```

`cost.json` 的输入模板：`python3 scripts/cost_table.py --example`

## 几条容易出错的地方

**1. 人数要乘对。** `unit_price × qty = 小计`。两个人的往返高铁是
`unit_price=842, qty=2, unit="人"`，不是 `unit_price=1684, qty=1`。
写清楚单价才能让用户核对。

**2. 住宿按「间·晚」不按「人」。** 2 人 1 间住 2 晚是
`unit_price=389, qty=2, unit="晚"`，不是 `qty=4`。

**3. 跨天项不要硬塞进某一天。** 住宿不填 `day`，它会自动进「未分摊」行。
硬分到 Day 1 会让按天分摊失真。

**4. 火车票价含多个席别时，说明取的是哪档。**
同程返回 `硬座¥264，硬卧¥456，软卧¥717`，`extract_visual_json.py` 取第一档（最低）。
选了别的席别要在 `detail` 里写明，否则用户对不上账。

**5. 报价占比要看。** `cost_table.py` 会输出「报价占总预算 N%」。
低于 60% 说明这份预算主要靠猜，值得在报告里提醒用户。
