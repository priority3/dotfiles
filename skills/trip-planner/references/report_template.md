# 报告结构

三套骨架：**跨城**（含往返大交通与住宿）、**周边游**（基地城市往返近郊）、
**本地**（只在一个城市内玩）。判定规则见 SKILL.md 的 Phase 0.2。

共同的硬性要求：同程 `markdown` 原文必须完整出现在「资源与预订」节，
一字不改（见 `tc_contract.md`）。

## 周边游骨架

文件名：`{基地}周边{时间}攻略.md`

以基地城市为起点终点，重点是「去哪」和「多远」。与跨城版的差异：

- 速览表把「往返」换成 **「目的地 + 车程」**，这是周边游的头号信息
- 「路线方案比选」是**按目的地**比，不是按风格比（见 plan_compare.md 第二节）
- 未选中的其他候选目的地**保留一句话摘要** —— 用户可能下次去
- 当天往返的方案没有住宿节

**周边游特有的必写项**：

1. **返程末班时间** —— 景区末班车/高铁末班，错过就回不去了
2. **车程写清楚方式** —— 「高铁 30min」和「自驾 2h」是完全不同的体验
3. **景区内部交通** —— 山地景区的索道/摆渡车常常另收费且耗时
4. **季节玩法** —— 同一个地方冬夏两副面孔，按出行日期描述

## 写作要求

**表格优先于段落。** 时间、地点、价格、交通这类信息放表格里，
用户扫一眼就能用。大段抒情文字对出行没有帮助。

**每个地点都要能落地。** 写「某某公园」不如写
「某某公园（地铁2号线 A 口步行 300m，免费，8:00-18:00）」。
写不出这些细节说明调研不够，回去补。

**时间要算得过来。** Day 1 排了 5 个站点，就要能说清怎么从第 3 站到第 4 站、
花多久。排不下就砍站点，不要留给用户去发现行程不可行。

**不确定的信息要标出来。** 价格、营业时间、活动日期这类会变的信息，
如果来自搜索结果而非实时接口，写明「据 {来源}，出行前请二次确认」。

**不编造。** 接口没返回的价格、余票、开放时间，就说没有，
不要用「一般来说」补一个看起来合理的数字。

## 交付时告诉用户什么

1. 报告文件路径
2. 地图 HTML 路径 + 「双击打开」
3. 人均花费与报价占比
4. 需要提前预约/购票的事项
5. 已知限制（哪些信息没查到、哪些需要二次确认）
