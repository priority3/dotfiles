# 方案比选模板

本 skill 的核心增量：不直接给一份行程，而是给 **2-3 条风格不同的候选**，
让用户挑完再落地。挑之前不生成地图、不算细账 —— 那些开销要花在选定的方案上。

---

## 候选方案的设计原则

**方案之间必须真的不同。** 三条都是「上午景点下午商场」只是换了名字，
用户无从选起。

比选的**维度**取决于模式：

| 模式 | 比什么 | 因为 |
| --- | --- | --- |
| 跨城 / 本地 | **风格**（经典 / 深度 / 主题） | 目的地已定，变的是怎么玩 |
| 周边游 | **目的地**（去哪个区县） | 用户不知道去哪，这才是他要的答案 |

---

## 一、按风格比选（跨城 / 本地）

差异要落在可感知的维度上：

| 维度 | 方案 A 倾向 | 方案 B 倾向 | 方案 C 倾向 |
| --- | --- | --- | --- |
| 节奏 | 紧凑，一天 4-5 站 | 松弛，一天 2-3 站 | 看人群定 |
| 花钱 | 该花花（直飞、市中心酒店） | 省（高铁、地铁沿线快捷） | 中等 |
| 内容 | 必去地标打卡 | 街巷/在地生活 | 主题化（亲子/情侣/摄影） |
| 移动 | 打车为主 | 地铁 + 步行 | 混合 |

常用三档（按用户画像调整，不必照搬）：

- **A 经典打卡** — 首次到访，把知名景点走一遍，节奏偏紧
- **B 深度 citywalk** — 来过或不爱人挤人，老城区步行 + 在���餐饮，花费最低
- **C 主题定制** — 按用户说的偏好（带娃 / 情侣 / 拍照 / 美食）重组

用户已明确说了偏好（"带孩子"、"想省钱"），就**不要**再给无关的那一档，
换成同一偏好下的两种不同实现（亲子方案里，室内博物馆 vs 户外乐园）。

---

## 二、按目的地比选（周边游）

每个方案 = 一个（或一组相邻的）区县 + 该地的行程 + 费用。
候选区县来自 `group_by_area.py` 的输出。

选方案时优先考虑这几点的差异：

| 维度 | 说明 |
| --- | --- |
| **车程** | 1h 以内 / 1-2h / 2h+，直接决定当天能否往返 |
| **天数** | 车程近的给「当天往返」，远的给「2天1晚」—— 这本身就是重要选项 |
| **主题** | 自然山水 / 古镇人文 / 温泉度假 / 亲子乐园 |
| **花费** | 门票+住宿差异往往很大（免费的西岭雪山 vs ¥80 的都江堰） |

```markdown
## 🧭 成都周边三个去处

| | A · 都江堰+青城山 | B · 西岭雪山 | C · 街子古镇 |
| --- | --- | --- | --- |
| **区域** | 都江堰市 | 大邑县 | 崇州市 |
| **车程** | 高铁 30min | 自驾 2h | 自驾 1h |
| **主题** | 水利古迹 + 道教名山 | 高山草甸 / 滑雪 | 古镇慢生活 |
| **建议天数** | 2天1晚 | 2天1晚 | **当天往返** |
| **门票** | ¥80 + ¥90 | ¥0（索道另计） | 免费 |
| **住宿** | ¥185-349 | ¥138-587 | 不需要 |
| **🟢 报价合计** | ¥738 | ¥596 | ¥120 |
| **🟡 估算合计** | ¥520 | ¥600 | ¥260 |
| **人均** | **¥629** | **¥598** | **¥190** |
| **适合** | 第一次去周边 | 想看自然/玩雪 | 只有一天空闲 |

> 车程为从成都市区出发的参考值；报价来自同程实时查询。
```

每个方案下附一句话行程：

```markdown
**A · 都江堰+青城山**
- Day 1 高铁到都江堰 → 都江堰景区（半天）→ 古城区住宿
- Day 2 青城山前山（半天）→ 下午返程
```

**周边游特有的注意事项**：

- **车程必须写。** 周边游的核心决策因素就是「多远」，不写等于没说。
- **「当天往返」是个真选项。** 别三个方案都是 2 天 1 晚 —— 很多人只有一天。
- **淡旺季差异要提。** 西岭雪山冬天滑雪、夏天避暑，玩法完全不同；
  查询日期落在哪个季节，就按哪个季节描述。
- **自驾与公共交通给不同答案。** 用户没说就默认公共交通可达优先，
  并在备注里标明哪些点自驾更方便。

---

## 对比表的通用要求

- 一屏能看完，细节留到选定之后
- 人均价必须来自 `cost_table.py` 的实算，不能拍脑袋
- 最省的那条应比最贵的低 25% 以上，否则没有选择意义

---

## 怎么问用户

用 `AskUserQuestion`，一个问题，选项就是这几条方案：

- `header`：按风格比选用 `路线方案`；按目的地比选用 `去哪儿`
- 每个 option 的 `label` 是方案名（`A · 都江堰+青城山`）
- `description` 写清差异与人均价
- 推荐的那条放第一个，标注「(推荐)」并说明推荐理由

不要问「你觉得哪个好」这类空问题，也不要一次问超过一个问题
（住宿、交通的细节等选定方案后再定，多数情况下不必再问）。

---

## 选定之后

只对**选中的那条**做后续开销：

1. 抽取该方案的地点 → `places.json`（category 用 11 类字母 + A 住宿 / X 交通枢纽）
2. 写 `routes.json`，`stops` 按当天游览顺序排列
3. `geocode.py` → `inject_route.py` → `validate_route_map.py`
4. `cost_table.py` 出费用明细
5. 组装报告

没被选中的方案在报告里保留一句话摘要即可，不要整段展开 —— 用户已经排除了它们。

---

## 反面例子

❌ **三条方案花费一样**（¥2,890 / ¥2,910 / ¥2,880）—— 没有选择空间，
说明只是把同一批景点重排了顺序。至少让最省的那条比最贵的低 25% 以上。

❌ **方案里塞满「可选」** —— 「Day 2 可以去 A 或 B 或 C」等于没规划。
每天的站点要定死，备选放进 places 但不进 routes。

❌ **人均价拍脑袋** —— 对比表里的价格必须来自 `cost_table.py` 的计算，
不能凭感觉写个整数。三条方案就跑三次 `cost_table.py`。

❌ **选完还问一堆细节** —— 选定方案后直接干活。
除非缺关键信息（比如没有出发地无法查交通），否则不要二次打断。
